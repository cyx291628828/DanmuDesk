# DanmuDesk 优化工作文档

> 日期：2026-08-30
> 范围：连接链路性能优化 + 稳定性/正确性修复（功能不变）
> 结论先行：**热连接耗时从 3~12s 降到约 1.8s；「首次连接偶发 45s 超时失败」的根因已定位并修复；另修复 7 个正确性缺陷。**

## 1. 背景与目标

用户反馈两个核心问题：

1. **连接直播间慢**；
2. **有时连不上**。

要求：功能不变，优化性能，顺带排查解决其他问题。

## 3. 根因分析

### 3.1 【核心根因】页面同文档导航挂起 → executeJavaScript 被冻结

**发现过程**（自制 Electron 探针逐层隔离）：

1. 探针实测：`curl` 直连房间页 1.2s 返回完整 HTML；页面全部子资源（JS/CSS）均 0.2~1.5s 可达 → **网络无问题**。
2. 无任何改动的原版行为复现：`dom-ready` 触发后，`did-finish-load`（load 事件）2 分钟以上不触发 → `loadURL` 挂死（与历史日志的 45s timeout 一致）。
3. DevTools 协议排除法：网络请求全部完成（0 pending）、渲染进程 CPU 空闲（10s 仅 +0.2s，排除死循环）、无 JS 对话框。
4. **导航事件捕获**：`dom-ready` 后 0.9~1.0s，页面发起 1~2 个**同文档（in-place）导航**，该导航永远不完成。Chromium 在「导航进行中」会冻结 `executeJavaScript`，同时当前文档的 load 事件永不触发 → `loadURL` 挂死 → 签名桥初始化失败 → 连不上。
5. **修复验证**：`webContents.stop()` 终止挂起导航后，`executeJavaScript` 立即恢复，`frontierSign` 调用成功返回真实 X-Bogus（`6g0x0qS2SmCtwR3q`，16 位，格式正确）。

另一个关键实测数据：**`window.byted_acrawler.frontierSign` 在 dom-ready 后约 0.5s（全程 1.5s）就已就绪**——根本不需要等 load 事件，甚至不需要等页面加载完成。原实现却把「页面加载成功」当成了签名桥就绪的隐含前提。

### 3.2 其他性能根因

| # | 问题 | 影响 |
| --- | --- | --- |
| P1 | 换房间时签名窗口整页重载（`reloadToRoom`） | 每次切换直播间多等 3~12s，而签名环境与房间无关 |
| P2 | 隐藏窗口加载完整直播流（视频解码） | 内存 300~500MB、CPU 占用高，渲染进程易被系统 kill，之后重连全慢 |
| P3 | 首次连接固定抓两遍房间页（`getLiveInfo` 无 Cookie → 解析失败 → 重抓） | 多 1~3s |
| P4 | `fetchUser` 请求已下线的 `/dylive/` 路由，且失败会中断整个连接 | 多 1 次串行往返 + 无谓失败点 |
| P5 | 日志每行 `statSync` + 同步 `appendFileSync`（每条弹幕 2~3 行日志） | 高频弹幕时主进程事件循环被磁盘 IO 拖慢 |

### 3.3 正确性缺陷（排查中新发现）

| # | 缺陷 | 触发场景 |
| --- | --- | --- |
| B1 | 首次连接时 10s 连接超时定时器**形同虚设**：房间状态要等签名桥就绪后才进 `rooms` Map，定时器回调里查无此房直接 return | 所有首次连接 |
| B2 | 连接中点「断开」**无法真正取消**：同 B1（房间不存在，teardownRoom 提前 return），连接流程继续走完并照常推送 connected | 签名桥加载期间点取消 |
| B3 | 多房间共用一个全局 `connectTimer`，`startConnectTimer` 会清掉上一个房间的定时器 | 两房间并发连接 |
| B4 | 超时/取消触发 teardown 后，`connectRoom` 继续执行并照常建立连接：UI 先报「连接超时」又变「已连接」 | B1/B2 的连带表现 |
| B5 | DyCast 内部重连耗尽（3 次）后**只发 error 不发 close**：上层永远等不到关闭事件，房间卡片卡在「已连接」但实际已死，且不会触发主进程级自动重连 | 网络抖动/风控踢线 |
| B6 | 重连时 cursor 被 `_afterClose` **提前清空**，重连参数里 cursor 恒为空：文档声称的「断点续传」实际从未生效 | 所有 WSS 层重连 |
| B7 | 服务端踢线以外的 close（下播/手动断开/连接错误）只发状态不清理房间：rooms Map 泄漏，转发器不释放 | 下播等场景 |
| B8 | WSS 层重连无退避（失败立刻重试，3 次在 1~2s 内烧完），与风控对抗时加剧拒绝 | 弱网/风控 |

## 4. 改动清单（文件级）

### 4.1 `electron/signBridge.ts` —— 签名桥重构（核心）

| 改动 | 说明 | 对应根因 |
| --- | --- | --- |
| **新增 `sign-preload.js` 就绪信号** | 沙箱 preload 与页面共享主世界，每 100ms 检查 `window.byted_acrawler.frontierSign`，就绪即通过 IPC 上报主进程。不依赖 executeJavaScript，实测 1.5s 检出 | 3.1 |
| **`waitForAcrawler` 双通道 + 自愈** | 通道1：preload 信标（首选）；通道2：executeJavaScript 轮询，每次调用限时 2s，检测到挂起（调用 2s 不返回）→ `webContents.stop()` 终止挂起导航后重试 | 3.1 |
| **签名调用超时自愈** | `frontierSign` 调用限时 4s，挂起则 `stop()` + 重试（最多 3 次）；页面随时可能再次发起挂起导航，不能只靠初始化时处理一次 | 3.1 |
| **就绪后主动 `stop()`** | SDK 就绪后立即终止页面还挂着的导航，loadURL 挂死不再影响主流程 | 3.1 |
| **页面粘性复用** | 删除 `reloadToRoom` 整页重载逻辑：签名桥只需要任意直播间页面提供 JS 环境与 Cookie（签名参数由主进程传入、HTTP/WSS 不经过该页面），换房间零成本 | P1 |
| **屏蔽 media 资源** | `webRequest.onBeforeRequest` 取消 `resourceType === 'media'` 请求：隐藏窗口不需要播放直播，省掉视频解码内存/CPU，渲染进程不易被 kill | P2 |
| **加载失败自动重试** | 页面加载 + 就绪检测整体失败自动重试 1 次（历史日志显示手动重试几乎都能成功）；单次加载超时 45s → 30s | 连不上 |
| **渲染进程被 kill 后台自动重建** | `render-process-gone` 后延迟 2s 用上次房间号后台重建，下次连接免等整页加载；连续失败 3 次熔断，防崩溃死循环 | P2 |
| **就绪轮询提速** | executeJavaScript 兜底轮询间隔 1000ms → 250ms | P1 |

### 4.2 `electron/sign-preload.js`（新增）

只读 preload：轮询 `byted_acrawler` 就绪状态并 `ipcRenderer.send('signer:acrawler-ready')` 上报。
不改写任何页面全局（不 stub alert 等，避免影响 JSVMP 环境检测），沙箱模式运行。

### 4.3 `electron/core/dycast.ts` —— 弹幕客户端

| 改动 | 说明 | 对应 |
| --- | --- | --- |
| **重连耗尽补发 close 事件** | 超过 3 次重连后除 error 外补发 `close(1006, '重连多次失败')`，上层得以收尾并触发主进程级自动重连（带退避） | B5 |
| **WSS 重连退避** | 重连延迟 1s×n（上限 4s），`close()` 可取消在途延迟重连（代数校验防竞态） | B8 |
| **cursor 断点续传修复** | `_afterClose` 不再清空 cursor（重连要用最新游标）；重连参数 `cursor` 为空时回退 `firstCursor` | B6 |
| **Cookie 链预热** | `fetchConnectInfo` 先把签名分区 Cookie 合并进请求层（新增 `request.seedCookieChain`），房间页首次抓取即可命中可解析状态，免去固定双次页面请求 | P3 |
| **fetchUser 条件跳过 + 非致命化** | Cookie 链已有 `__ac_nonce/ttwid` 时跳过该请求；失败不再中断连接 | P4 |

### 4.4 `electron/core/request.ts`

新增 `seedCookieChain(cookies)`：签名分区 Cookie 合并进请求层 Cookie 链（外部值优先覆盖同名项）。

### 4.5 `electron/main.ts` —— 连接管理重构

| 改动 | 说明 | 对应 |
| --- | --- | --- |
| **房间状态提前创建** | `connectRoom` 入口即建房入 Map（沿用旧房间的过滤/统计/转发/主播信息），后续每个异步节点校验连接代数 | B1/B2 |
| **每房间独立连接超时** | `connectTimer` 移入 `RoomState`，多房间互不干扰；超时上限 10s → 150s（覆盖签名桥重试的极端情况；正常连接 1~5s，该兜底只拦截卡死）；超时同时推送 error 状态 + toast，超时/取消原因通过 `cancelReasons` 传回，UI 文案准确 | B1/B3/B4 |
| **取消真正生效** | 连接中「断开」→ teardownRoom 使连接代数失效 → connectRoom 在每个异步节点放弃收尾 | B2/B4 |
| **close 事件彻底清理** | 非服务端踢线的关闭（下播/手动/错误）走 `teardownRoom`，rooms Map 不再泄漏、转发器正确释放 | B7 |
| **处理 WSS 层重连成功事件** | 监听 DyCast `reconnect` 事件推送 connected 状态，UI 从「重连中」恢复；`reconnecting` 状态补带 roomId | 体验 |
| **连接代数改计数器** | `Date.now()` → 自增计数器，消除同毫秒并发连接撞号 | B4 |
| **退出前冲刷日志** | `before-quit` 调 `CLog.flush()` | P5 |

### 4.6 `electron/core/logUtil.ts` —— 日志批量落盘

- 移除**每行 statSync**：文件大小改内存记账（`setFileTarget` 时读一次），超 50MB 触发轮转（改名 app.log.1，Windows 占用导致的改名失败自动下轮重试）。
- 批量写入：日志行入内存缓冲，500ms 定时或攒满 8KB 冲刷一次（替换逐行 appendFileSync）。高频弹幕（每条消息 2~3 行日志）下磁盘系统调用从每秒数百次降到个位数。
- 连续写盘失败 5 次自动停用文件日志并清空缓冲（防内存堆积），业务不受影响。
- 新增 `CLog.flush()` 供退出前冲刷。

### 4.7 `renderer/app.js`（小修）

- 用户主动取消连接后，不再对 connect 返回的 `{ok:false}` 重复弹「连接失败」类 toast（保留「已取消连接」）。

### 4.8 `scripts/build.mjs`

- 构建时复制新增的 `electron/sign-preload.js` 到 `dist/`。

## 8. 遗留风险与后续建议

1. **签名窗口长期运行的内存增长**：粘性页面停留在直播间页，页面自身弹幕 DOM 会缓慢增长（media 已拦截，增速大幅下降）。渲染进程若被系统回收，现有后台自动重建会自愈；后续可加「定时软刷新」进一步兜底。
2. **`no-proxy-server` 强制直连**：纯代理网络无法使用。如需支持，可为 `ws`/`https.request`/`net.fetch` 统一接 http-proxy-agent（依赖已在 package.json 中，未接线）。
3. **风控对抗**：签名依赖真实页面 SDK，抖音升级 JSVMP 或页面结构（`__pace_f` 解析正则、internalExt 格式）时需跟进。`DEBUG_SIGN=1` 可视化调试页面。
4. **建议补 git**：项目当前无版本管理，本次优化前源码未留基线；建议立即 `git init` 提交，后续问题可 diff 定位。
5. **探针脚本**：本次排查用的临时探针已删除，方法论记录在本文档 §3.1，必要时可按同样思路重建。

## 9. 功能迭代记录：连接历史 + 发送弹幕（2026-08-30）

优化完成后同日追加两个功能，保持功能文档同步（详见 README「使用方法」§1/§4）。

### 9.1 连接历史（输入框下拉）

- **数据链路**：主进程 DyCast `open`（真实连接成功）→ `settings.addRoomHistory` 去重置顶、上限 20 条、持久化 `userData/settings.json` → IPC `danmu:history-get/clear`。
- **UI**：点击输入框弹出下拉（头像 + 主播名 + 房间号 + 上次连接时间；今天显示 HH:mm、昨天带"昨天"前缀、今年 MM-DD、往年完整日期），可视约 5 条滚动，支持清空，点击条目直接重连；点击面板外/Esc 关闭。原 localStorage「上次输入预填」由历史记录取代。
- **验证**：Electron 内单元测试通过（25 条截断到 20 / 重连置顶 / 昵称更新 / 旧头像保留 / 持久化）；真实应用 UI 实测（连接在播直播间 → 历史面板即时出现该房间条目）。

### 9.2 发送弹幕 + 定时重复发送

- **方案**：抖音 Web 发弹幕没有公开 API 可走，采用「签名窗口页面注入」（把签名窗口导航到目标直播间，向页面评论框写入内容并触发回车，与真人操作一致，风控最友好）。
- **v3 定案（2026-08-30，实测发送成功）——触发回车是整个功能的核心难点**：
  - 评论框是字节 **editor-kit 富文本编辑器**（React 受控组件），对「回车」的触发方式极其挑剔；
  - ❌ executeJavaScript 派发合成 KeyboardEvent：只写文本不发送（**旧版「内容已写入=true」是假成功，这就是当年功能被删的原因**）；
  - ❌ webContents.sendInputEvent keyDown Return：缺少 keypress 环节，编辑器不响应；
  - ❌ JS `.click()` 发送按钮：非信任事件且按钮无「发送」文字（图标按钮，找不到）；
  - ✅ **CDP `Input.dispatchKeyEvent`（keyDown 带 `text:'\r'`）**：Puppeteer 同款按键注入，完整还原 keydown+keypress，实测真实发出（聊天区出现「金大宝：666」、输入框清空）；
  - 成功判据：**输入框被清空**（失败时文本残留；旧版靠「内容已写入」判定属于假成功）。
- **v2/v3 排查中另修的两个致命 bug**：
  1. **beacon 过早 stop**：签名就绪信号一到就 `webContents.stop()`，把还在加载的文档杀掉，评论框模块永远不挂载（「页面无评论输入框」的根因）。现在页面加载期间主进程绝不做 stop，页面就绪全部由 preload 页面内上报；
  2. **onBeforeRequest 覆盖**：Electron 同一 session 的 `onBeforeRequest` 只保留最后一个监听器，多处注册会互相覆盖（探针的请求观测因此失效过）。
- **核心模块** `electron/danmuSender.ts`：
  - 所有发送（手动 + 定时、跨房间）过同一串行队列，强制 ≥3s 冷却；
  - 发送前校验登录态（cookie + 页面侧评论框渲染双重确认）；
  - 触发链：CDP Enter → char '\r' → sendInputEvent Return → 合成事件 → 点击按钮，每步以「输入框清空」验证；
  - 页面登录态失效自愈：找不到评论框时强制重载签名页面重试一次；
  - 每次页面 JS 执行带超时，挂起导航冻结时 `stop()` 自愈（仅限页面渲染完成后的冻结恢复）。
- **定时发送**：主进程内存任务（会话级，重启不自动续发），开启立即发一次后按间隔（5~3600s）重复；结果经 `danmu:send-status` 推送 UI；房间断开自动停止。
- **signBridge 配套**：`ensureSignerOnRoom`（发送专用按需导航 + `waitForChatReady` 等评论框真实渲染）、`execInSignerPage`（超时自愈执行）、`getSignerWebContents`；签名路径的粘性复用不受影响。
- **端到端实测（2026-08-30）**：生产应用中向在播直播间 338043429744 发送成功——日志 `[sender] 弹幕已发送`，聊天区出现「金大宝：666」，输入框清空，定时/手动两条链路均验证通过。**前提：右上角登录抖音**（未登录时页面无评论框，发送会明确报错提示登录）。
- **启动器日志净化（同日）**：无独显/虚拟机环境下 Chromium 初始化软件渲染会打 `Failed to create GLES3 context` / `Failed to create shared context for virtualization` 等 ERROR——是自动回退 GLES2 的无害噪音，源头无法关闭。`scripts/launch.cjs` 改为 pipe stderr 并按已知无害模式过滤（缓冲拼接防止截断行误伤），其余输出原样透传，真实报错不受影响。

### 9.5 发送自愈：账号异动后发不出弹幕（2026-08-30 傍晚）

**用户场景**：软件内登录抖音账号后，用手机（同账号）进其他直播间，之后软件发不出弹幕。

**根因分析**：发送依赖长驻的签名窗口页面（粘性页面设计）。账号在其他设备活动后，抖音服务端可能轮换会话/标记风控，长驻页面的会话状态随之过期。此前代码的两个缺口：
1. 发送被服务端**静默拒绝**时（回车后输入框不清空，stage=unverified），直接报错放弃，**不会重载页面**——而过期的页面状态只有整页重载才能恢复；
2. 若 sessionid 被服务端轮换，页面加载后变为未登录（无评论框），但主进程 Cookie 检查只看「cookie 存在与否」仍显示已登录，用户界面永远显示已登录却发不出去，**没人提示重新登录**。

（日志中当天实际出现的失败均为多房间任务切换时的页面未就绪，已有重载自愈兜住；手机场景属于上两个缺口，尚未在日志中留下记录。）

**修复**（`danmuSender.doSend` 重试框架重构）：
1. **可自愈失败扩展**：`no-input`（无评论框）与 `unverified`（回车后未清空，服务端静默拒绝）都触发「强制重载签名页面 → 重试一次」——整页重载会用当前 Cookie 重新握手会话、重建登录态和编辑器；
2. **登录态失效检测**：重载后仍无评论框时，调 `webcast/user/me/` 校验：若服务端判定未登录（20003）→ 自动清除登录 Cookie → 回调主进程推送 `danmu:login-status {loggedIn:false}` → 界面恢复未登录态并提示「登录已失效，请重新登录」（不再出现「显示已登录却永远发不出」的死局）；
3. **拒绝原因可读**：发送失败时抓取页面 toast 文本（如「发言频率过快」「需要关注主播」）拼进错误信息。

**结果**：手机活动导致的三种情形现在都有出路——页面态过期 → 重载自愈；会话被轮换 → 检测+清除+明确提示重新登录；真被限言/粉丝团限制 → 带页面提示的准确报错。

### 9.6 「一键启动打不开软件」：隐藏窗口导致的无界面僵尸实例（2026-08-30 晚）

**现象**：点一键启动后命令窗打印「应用已在运行中，本次启动已退出」然后关闭，软件窗口不出现。

**根因**：用户关闭主窗口（×）时，签名桥的**隐藏窗口**仍然存在 → Electron 的 `window-all-closed` 永不触发 → 应用不退出，变成**无界面僵尸实例**，持续占用单实例锁。此后每次启动的新实例都被锁挤出（控制台一行提示后闪退），表现为「打不开」。该问题自引入签名桥隐藏窗口起就潜伏；经 bat 启动时关闭控制台会连带杀掉进程树，掩盖了它——单独关窗口后即可复现（进程列表可见 6 个无窗口的 electron 进程）。

**修复**：`mainWin.on('closed')` 中主动 `app.quit()`（Windows 惯例：关窗口即退出应用），`before-quit` 里现有的 `teardownAllRooms + disposeSigner + CLog.flush` 会把隐藏窗口、弹幕连接、定时任务、日志缓冲一并清理。

**验证**：启动新实例 → 关闭主窗口 → 进程全部退出（此前会残留 6 个无窗口进程）；再次启动正常获取锁、窗口正常出现。

### 9.8 软件授权系统（2026-08-30 晚，用于售卖）

**方案**：离线签名授权码（Ed25519 非对称签名）——机器绑定 + 有效期 + 版本上限 + 3 天试用，无需服务器；接口已按「在线激活/心跳」预留升级路径（未来在 `activateLicense` 前置服务端校验即可，客户端架构不变）。

**组成**：
- `electron/license.ts`：验签（内置公钥）、机器码（SHA-256(MachineGuid) 前 16 位，显示 XXXX-XXXX-XXXX-XXXX）、到期日/版本上限校验、试用期（`TRIAL_DAYS=3`）、时间回拨锁定（状态文件记录见过的最大时间，回拨超 48h 锁定）；
- 门禁：`danmu:connect` / `danmu:send` / `danmu:schedule-add` 未授权时拒绝并引导激活；30 分钟定时复检（试用到期无需重启即生效）；
- UI：顶部授权标识（未激活/试用·剩N天/已授权/已过期，临期闪烁提醒）+ 点击弹出的授权弹窗（机器码复制、授权码激活）；
- **卖家工具** `scripts/license-gen.cjs`（不打包进软件）：
  - `node scripts/license-gen.cjs genkey` 首次生成密钥对（私钥 `license-private-key.pem` 勿外泄、已加 .gitignore）；
  - `node scripts/license-gen.cjs gen --machine <买家机器码> --days 365 [--maxver 0.9] [--name 备注]` 生成授权码；
  - `--maxver` 版本上限：抖音改版后旧破解版自然失效，正版联系卖家更新授权——比加密更实用的保护；
- 渲染层不可信原则：校验逻辑全在主进程。

**实测**（CDP 驱动真实 IPC）：试用态（剩3天/标识正确）✓、错误机器码拒绝 ✓、过期码拒绝 ✓、篡改签名拒绝 ✓、正确激活（标识变「已授权」+366 天）✓。

**已知边界（诚实声明）**：Electron 应用无绝对防破解，本方案挡的是「授权码外传、改系统时间白嫖、随手解包改码」三类实际场景；更强对抗可后续加 bytenode 字节码编译 + 在线心跳。

**售卖流程**：买家安装软件 → 授权弹窗复制机器码发给你 → 你跑 license-gen 生成授权码发回 → 买家粘贴激活。自己的机器可 `--days 3650` 签一个长期码。
